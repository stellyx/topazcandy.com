# $450 website package cart

All six template purchase banners and the homepage/catalog offer open this shared cart. `config.mjs` is the single payment destination for the cart. Template query values are allowlisted and cannot change the package price, currency or payment destination.

The approved offer is $450 USD for one website using a selected design, setup and launch, SEO setup, eligible Google Maps/Business Profile setup or cleanup, business-information and link checks, and three months of website service and maintenance from launch. The included care covers the agreed website and its existing content. AI agents, automation, ongoing AI services, new features, domain registration, paid hosting and third-party subscriptions are agreed separately. Search Console/sitemap/indexing submission is a launch task with owner access; Google controls actual indexing and ranking.

## Current payment and email behavior

The owner requested use of the existing personal PayPal account. A classic hosted Buy Now button was created there on 2026-10-11: `H48437LCHWWFQ`, product `TOPAZ-WEBSITE-450`, with a saved price of $450.00 USD, one item, $0 shipping and no customer shipping-address request. The account was not converted to a business account. All six design options use that same fixed product price.

The checkout has one visible form before payment, displayed in three compact steps: contact details, addresses, then review and payment. Optional phone/website/notes and address line 2 are collapsed; hidden steps keep their values. Enter advances through a validated step without sending intake. Final validation reveals any invalid hidden field before reporting it. US and Australian postal fields request a numeric keyboard, Canadian/UK/international postal fields retain text entry, and phone/email/website fields use matching input modes. Website domains can be entered without https://; the application normalizes and validates the URL. The extra-services links are removed from checkout and all purchase banners; the main site prominently presents the broader service catalogue before checkout. It requires business and contact names, a valid email address and a business address, with a billing-address-is-the-same option. Separate billing addresses can be entered. Client-side checks validate email, optional phone/website, country, state/province and country-specific postal-code formats. These are input and format checks, not proof that a mailbox or physical address exists. Address entry supports 249 country/territory choices; complete physical address verification is not installed.

The activated FormSubmit AJAX endpoint sends the intake to the established Topaz Candy business mailbox behind the scenes. It uses the provider's documented public opaque destination, not an account credential or private API key. The recipient is fixed; visitors cannot choose a destination or CC. The request is form-encoded so it uses a simple cross-origin POST without a preflight. Contact details, business and billing addresses, selected design, full notes, package scope and an order reference are included in the email. The submission is explicitly awaiting payment verification, so abandoned checkout is not mistaken for a paid order. FormSubmit is the email processor and documents a 30-day submission archive. No FormSubmit archive API key was requested, and no customer data is stored in browser storage or the repository.

Only a positive provider response allows the same-tab PayPal handoff. Failures and timeouts preserve the form and block payment. Controls are disabled during submission; an accepted unchanged intake is reused in page memory on retry rather than sent twice. A honeypot rejects filled trap fields. The selected design and order reference are passed to the saved PayPal button through its generated option fields and the custom reference field. Long option values remain within 200 UTF-16 units without splitting emoji. The package price and recipient stay hosted in PayPal. An order reference and accepted intake do not prove payment.

A live activation email was received and the endpoint activated. Two labelled synthetic delivery tests arrived in the business mailbox with the selected design, reference and both addresses. The final test used the actual `validateIntake`/`intakePayload` code and the same form-encoded transport as the page; the provider returned HTTP 200, success=true and Access-Control-Allow-Origin: *. No real customer addresses were used, no outreach was sent and no payment was made. The storefront no longer asks the buyer to open their email app, supply a transaction ID or send details after paying.

PayPal's receive-payment email setting was previously confirmed enabled/read-only. Receive-payment SMS was enabled and verified after reloading settings. Those transaction alerts remain separate from the new automatic intake email. A completed payment, actual PayPal transaction alert and app push were not tested.

Do not treat a return URL/query string, opening PayPal, clicking an email link, or an entered transaction ID as proof of payment. The operator confirms the payment in PayPal before starting work. Automatic paid-status handling still requires verified server-side notifications; do not enable IPN against static GitHub Pages.

The older owner-provided QR destination was replaced by this fixed-price hosted checkout. No PayPal.Me handle was guessed or created. Provider reference: https://developer.paypal.com/api/nvp-soap/paypal-payments-standard/integration-guide/Appx-websitestandard-htmlvariables/
